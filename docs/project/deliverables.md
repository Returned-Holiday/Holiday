## 개발기획서와 서비스 개요서의 차이

| | 개발기획서 업데이트본 | 서비스 개요서 |
|---|---|---|
| 제출 부문 | 개발 | 보안 (소스코드와 함께) |
| 읽는 사람 | 심사위원 | 소스코드 진단원 (추정) |
| 양식 | 정해져 있음: 1장 추진배경, 2장 주요 기능·개발환경, 3장 활용방안·기대효과 | **없음 — 디스코드 확인 필요** |
| 핵심 질문 | 왜 필요하고, 무엇을 만들었고, 어떤 효과가 있나 | 시스템 구조, 데이터 흐름, 보안 처리가 코드 어디에 있나 |
| 톤 | 설득 | 기술 요약(표, 구조도, 경로) |

- **구조적 설계 점수는 기획서 2장에서 받는다.** 개요서에만 쓰고 기획서에서 빼면 안 된다.
- 개요서는 같은 설계를 코드 위치까지 내려서 쓴다.
  - 기획서: "역할 기반 접근 제어와 객체 단위 검증으로 IDOR를 방지한다"
  - 개요서: "`Back/apps/common/permissions.py`의 권한 클래스를 모든 회원 API가 사용. 적용 API 목록은 표 2"
- 두 문서 모두 `docs/security.md`를 원본으로 삼는다.

## 서비스 개요서 추천 목차 (양식이 없을 경우, 5~8쪽)

| # | 항목 | 재료 |
|---|---|---|
| 1 | 서비스 개요, 사용자 유형 | 기획서 1장 |
| 2 | 기능 목록: 기능 → API → 접근 가능한 역할 | `docs/features.md`, `docs/api.md` |
| 3 | 시스템 구성: 아키텍처도, 기술 스택·버전 | 기획서 3·4장, `infra/CLAUDE.md` |
| 4 | 데이터 흐름: 개인정보 입력 지점과 처리·저장·폐기 경로 | `docs/security.md` |
| 5 | 소스코드 구조: 폴더 지도, 진입점, **공통 보안 모듈 위치** | 레포 구조 |
| 6 | 보안 설계: 위협 → 대책 → 구현 위치 | `docs/security.md` |
| 7 | 점검·조치 결과: 도구, 탐지·조치 건수, 미조치 사유 | 최종 스캔 결과, GitHub Issues |
| 8 | 실행 방법, 테스트 계정 안내(비밀번호는 문서에 쓰지 않음) | `README.md` |

5·6번이 핵심이다. 진단원이 "권한 체크는 공통 모듈 한 곳"임을 알면 그 모듈을 확인하는 방식으로 진단한다.

## 소스코드 최종 정리 체크리스트 (10/27–28, BE-B)
- [ ] `.env`, 키·비밀번호, `node_modules`, `dist`, `__pycache__`, 로그 파일이 들어가지 않았다

- [ ] `package-lock.json`, 해시 고정된 `requirements` 파일이 들어 있다
- [ ] `README.md`에 실행 방법이 있다
- [ ] 최종 Semgrep·Bandit·pip-audit·npm audit 결과 캡처(개요서·PPT 재료)
- [ ] SBOM(CycloneDX) 생성
- [ ] 프론트 운영 빌드에 소스맵이 없다
